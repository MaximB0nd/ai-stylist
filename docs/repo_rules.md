# Правила ведения репозитория

Эти правила помогают держать кодовую базу в порядке, а историю изменений — чистой и понятной.

## Работа с кодом

- Комментарии в коде пишем только на английском языке.
- В каждой части проекта используем линтер, который принят и настроен именно для неё.
- Не добавляем новый линтер и не меняем его конфигурацию без согласования с командой.
- Перед коммитом прогоняем линтер для изменённого кода. Коммитим только после прохождения проверки без ошибок.

## Issues

### Формат заголовка

Заголовок issue состоит из двух частей, разделённых двоеточием:

```text
<SEGMENT>-<NUMBER>: <short description>
```

Первая часть содержит:

- `SEGMENT` — приставку той части репозитория, к которой относятся изменения;
- `NUMBER` — последовательный номер задачи внутри выбранного сегмента.

Используем только следующие сегменты:

- `BACK` — backend;
- `FRONT` — frontend;
- `AI` — нейросети и связанная с ними логика;
- `COMMON` — общие задачи, не связанные с разработкой.

Перед созданием issue находим последний номер с такой же приставкой и используем следующий: `<LAST_NUMBER> + 1`. Нумерация каждого сегмента ведётся независимо.

Вторая часть — короткий комментарий о том, что будет реализовано в рамках issue. Заголовок должен быть понятен без чтения полного описания.

Примеры:

```text
FRONT-12: Add outfit upload form
BACK-7: Validate uploaded images
AI-4: Improve styling recommendations
COMMON-3: Describe repository workflow
```

### Содержание issue

- В описании подробно фиксируем, что именно нужно сделать в рамках issue и какой результат ожидается.
- Добавляем важный контекст, ограничения, ссылки и примеры, если они помогут разобраться в задаче без дополнительных вопросов.
- По возможности указываем критерии готовности, по которым можно проверить выполнение задачи.
- Желательно оформлять заголовок и описание на английском языке, но это не обязательное требование.
- Один issue — одна самостоятельная задача. Если задача слишком большая, декомпозируем её на sub-issues и выполняем их последовательно.

## Ветки

Каждую рабочую ветку привязываем к issue. Используем следующий формат:

```text
<SEGMENT>-<NUMBER>[-<optional-description>]
```

- В начале названия указываем первую часть issue: сегмент и последовательный номер задачи.
- Описание добавляем опционально после дефиса.
- Описание пишем на английском языке строчными буквами.
- Вместо пробелов используем дефисы.
- Название должно быть коротким и передавать суть задачи.

Примеры:

```text
FRONT-12
FRONT-12-add-outfit-upload
BACK-7-fix-image-validation
```

## Коммиты

### Формат сообщения

Каждый коммит обязательно привязываем к issue:

```text
<SEGMENT>-<NUMBER>: <short comment>
```

Требования к сообщению:

- пишем только на английском языке;
- коротко описываем результат изменения, без воды;
- по возможности укладываем всё сообщение примерно в 50 символов;
- используем первую часть реального issue — коммиты без issue не допускаются.

Хорошие примеры:

```text
FRONT-12: Add outfit upload form
BACK-7: Fix image validation
AI-4: Improve styling recommendations
```

Плохие примеры:

```text
Add feature
FRONT-12: Добавлена форма загрузки образа
BACK-7: Fixes
AI-4: Add model, refactor API and update docs
```

### Состав коммита

- Один коммит — одна фича или одно логически завершённое изменение.
- Небольшие связанные правки можно собрать в один коммит, если отдельно они не несут пользы.
- Не смешиваем в одном коммите несвязанные фичи, рефакторинг и случайные фиксы.
- Большой PR декомпозируем на последовательные логические коммиты, которые удобно читать и ревьюить.

## Pull request

- Один PR решает одну задачу или объединяет изменения вокруг одной цели.
- Большой PR разбиваем на логические коммиты — не складываем всё в один огромный коммит.
- Описание PR необязательно, если назначение изменений понятно из title и истории коммитов.
- Если контекст, ограничения или способ проверки неочевидны, лучше кратко указать их в описании PR.
