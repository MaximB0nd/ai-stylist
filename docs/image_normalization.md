# Проверка и сохранение изображений в PNG

Новые исходники и результаты генерации сохраняются как настоящий PNG с расширением
`.png` и `Content-Type: image/png`. JPEG и WebP принимаются на входе, но конвертируются
перед сохранением. Подмена расширения без преобразования байтов не используется.

## Исходные фотографии

`GenerationService` получает общий слот обработки до чтения фотографии. Проверяет
обязательность файла, заявленный MIME и ограниченный объём входа. Затем Pillow
определяет формат по содержимому, проверяет соответствие MIME, структуру файла,
декодирование, размеры и отсутствие нескольких кадров.

Обе фотографии проверяются и нормализуются до первой загрузки в MinIO. Ключи:

```text
sources/{user_id}/{generation_id}/face.png
sources/{user_id}/{generation_id}/body.png
```

AI Core получает JSON со временными подписанными ссылками на эти объекты, а не
Base64 или бинарный multipart. После сохранения параметров задачи recovery
повторно использует те же ссылки и тело запроса, не кодируя исходники заново.

Если один PUT завершается ошибкой, backend пытается удалить оба объекта, для
которых уже начиналась загрузка: ошибка ответа не доказывает, что PUT не состоялся.
При недоступном MinIO немедленная очистка может не сработать; остаётся lifecycle
для `sources/`. При неоднозначной ошибке сохранения альбома объекты не удаляются:
commit мог завершиться и оставить на них ссылки в БД.

## Нормализация

Общий модуль: `src/backend_core/app/services/image_service.py`.

- Исправляет ориентацию EXIF перед удалением метаданных.
- Преобразует в RGB либо RGBA с сохранением прозрачности; цветовую палитру раскрывает.
- При наличии ICC преобразует цвет в sRGB; некорректный профиль отклоняется.
- Удаляет EXIF, текстовые и прочие исходные метаданные.
- Сохраняет разрешение без автоматического масштабирования.
- Записывает PNG с `compress_level=3`, `optimize=False`.
- Уже подходящий 8-битный RGB/RGBA PNG полностью проверяется, но возвращается без
  повторного кодирования, если содержит только IHDR/IDAT/IEND и не имеет хвостовых данных.

16-битный PNG отклоняется: не выполняется неявное обрезание значений до 8 бит.
PNG использует сжатие без потерь; это не уменьшает артефакты исходного JPEG и
не гарантирует меньший размер файла, чем у JPEG или WebP.

## Лимиты и ресурсы

| Ограничение | Значение |
|---|---|
| Загрузка исходного файла | Не более 10 МиБ |
| Скачивание результата ИИ или legacy-объекта | Не более 15 МиБ |
| Размер каждой стороны | 1–4096 пикселей |
| Итоговый PNG | Не более 15 МиБ |
| Число кадров | Один |
| Потоки преобразования | Два на процесс backend |

PNG-вывод ограничивается во время записи в буфер, а не только после её завершения.
Растровые буферы декодирования дополнительно занимают память в зависимости от
разрешения и числа каналов. Размер файла в 10 МиБ не означает расход памяти 10 МиБ.

Асинхронные вызовы преобразования выполняются в отдельном ThreadPoolExecutor.
Для источников слот удерживается также на время загрузки и создания альбома,
чтобы ожидающие запросы не накапливали готовые PNG при сбое хранилища. Результаты
сохраняют существующее ограничение одновременно обрабатываемых изображений.
При отмене преобразования backend дожидается фактического окончания работы
потока перед освобождением слота. При нескольких процессах лимиты действуют
отдельно для каждого процесса, а не на весь Docker-кластер.

## Результаты и legacy callback

`generation_results.py` сначала ограниченно скачивает исходный файл и проверяет
переданную AI Core SHA-256 по исходным байтам. Затем нормализует изображение и
загружает PNG под изолированным префиксом попытки:

```text
albums/{album_id}/{token}/look_00.png
```

Проверка checksum выполняется до конвертации: у полученного PNG может быть другая
контрольная сумма. ACK отправляется только после сохранения фотографий и статуса
COMPLETED одной транзакцией. Повреждённая картинка не приводит к COMPLETED или ACK.

Legacy callback сохраняет входной список ключей в durable inbox, затем ограниченно
скачивает эти объекты и создаёт новые PNG в префиксе текущей попытки. Recovery
использует ту же обработку; прямого сохранения непроверенных ключей в Photo нет.
Первоначальные legacy-объекты автоматически не удаляются, поскольку их владельцем
может быть другая операция. Ошибки транспорта допускают повтор, неверное содержимое
завершает обработку ошибкой. Новые неиспользуемые объекты очищаются существующей
проверкой ссылок в PostgreSQL; при недоступной БД очистка откладывается.

## Ошибки запроса генерации

- `400` — неподдерживаемый MIME, несовпадение MIME с содержимым, повреждение,
  анимация, недопустимые размеры, разрядность или профиль.
- `413` — исходник больше 10 МиБ либо нормализованный PNG больше 15 МиБ.
- `422` — отсутствующая обязательная фотография.
- `502` — неудачная загрузка проверенных исходников в хранилище.

## Совместимость и проверки

Существующие объекты не перекодируются, их ключи в БД не меняются. Новая SQL-миграция
для PNG не нужна. При необходимости конвертация старых альбомов должна выполняться
отдельно с обновлением ссылок и безопасным удалением старых объектов.

```bash
cd src/backend_core
python -m pip install -r requirements.txt
python -m pytest tests/test_image_service.py -v
python -m pytest tests -q
```

Для Docker нужно пересобрать backend, чтобы установить Pillow:

```bash
docker compose up -d --build backend_core
```

Тесты используют маленькие настоящие изображения вместо одних magic bytes.
Проверяют форматы, повреждения, ориентацию, прозрачность, ICC, лимиты, отмену,
неизменность готового PNG, очистку и порядок checksum/ACK. Сравнение скорости
разных уровней сжатия на пользовательских фотографиях ещё не выполнялось.
