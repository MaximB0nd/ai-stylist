# Backend и AI Core на разных ПК в локальной сети

## Какие адреса заменить

При запуске через Docker Compose редактируйте `.env` в корне репозитория.
При запуске backend непосредственно через Python — `src/backend_core/.env`.
В обоих локальных файлах и соответствующих `.env.example` подготовлены заглушки:

```dotenv
AI_CORE_URL=http://ai-core-pc.invalid:8001
MINIO_AI_ENDPOINT=backend-pc.invalid:9000
```

`.invalid` намеренно не является рабочим адресом. Завтра замените:

- `ai-core-pc.invalid` — на LAN IPv4 ПК с AI Core; `8001` — на фактический порт его HTTP API.
- `backend-pc.invalid` — на LAN IPv4 ПК с backend и MinIO. Порт `9000` — S3 API.

Например, если backend находится на `192.168.1.10`, а AI Core на `192.168.1.20`:

```dotenv
AI_CORE_URL=http://192.168.1.20:8001
MINIO_AI_ENDPOINT=192.168.1.10:9000
```

Это пример адресов, а не автоматически определённая конфигурация вашей сети.
Не добавляйте `http://` к `MINIO_AI_ENDPOINT`: формат — `host:port`.
В текущем публичном контракте AI Core исходники принимаются по HTTP;
для этой конфигурации используется `MINIO_SECURE=false`.

`MINIO_ENDPOINT` остаётся внутренним адресом: `minio:9000` в Compose либо
`localhost:9000` при локальном запуске. По нему backend читает и записывает файлы,
а также определяет регион бакета. `MINIO_AI_ENDPOINT` используется только для
подписи ссылок, передаваемых AI Core: адрес уже входит в подпись, заменять его
после генерации ссылки нельзя. Если настройка отсутствует, сохраняется прежнее
поведение — ссылки подписываются с внутренним адресом.

`MINIO_PUBLIC_ENDPOINT` — отдельный адрес для браузера. Если браузер открыт
на том же ПК, допустим `localhost:9000`; для браузера на другом устройстве
укажите LAN IP backend. Порт `9001` открывает консоль MinIO и не используется
для скачивания исходников.

## Применение

После подстановки адресов из корня проекта:

```bash
docker compose up -d --build backend_core
```

Compose передаёт оба параметра backend. Команда запуска сервиса уже выполняет
`alembic upgrade head` перед Uvicorn. Добавлена миграция `0007`: сохранение
ожидающего ACK и времени следующей попытки. Удалять контейнеры, бакет или том
PostgreSQL не требуется. При запуске без Docker выполните из `src/backend_core`:

```bash
python -m alembic upgrade head
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Подстановка адресов применяется к новым генерациям. У уже отправленных задач
JSON запроса и подписанные ссылки сохраняются неизменными для корректной
идемпотентности; старую задачу с неверным адресом нельзя исправить заменой ENV.

## Что проверить на двух ПК

1. AI Core слушает LAN-интерфейс (`0.0.0.0`), его API-порт разрешён брандмауэром.
   С ПК backend открываются `/health/ready` и `/v1/capabilities` AI Core.
2. На ПК backend входящий TCP `9000` доступен ПК с ИИ. Compose уже публикует этот
   порт. Настройка приложения не меняет Windows Firewall и маршрутизацию.
3. На AI Core разрешён точный origin исходников, например `http://192.168.1.10:9000`.
   Подписанная ссылка на PNG скачивается с ПК с ИИ без изменения адреса и query.
   Ссылки действуют 3600 секунд по умолчанию; это должно удовлетворять
   `input_urls.min_ttl_seconds` из capabilities. Часы на ПК должны быть согласованы.
4. Backend может скачать `download_url`, который возвращает AI Core: в нём тоже
   должен быть доступный с ПК backend адрес, а не `localhost` чужого ПК.
5. AI Core допускает текущий сценарий без обязательного drape_test. Если этот
   вход обязательный в его конфигурации, нужна отдельная доработка сценария.
6. Выполнить настоящую генерацию пяти изображений и открыть их из браузера.
   `/health` backend проверяет PostgreSQL и MinIO, но не подтверждает весь путь AI.

## Восстановление доставки

Фотографии, статус `COMPLETED`, remote job ID и признак `results_ack_pending`
сохраняются одной PostgreSQL-транзакцией. Только после успешного commit backend
отправляет `POST /v1/jobs/{job_id}/results/ack` без тела. До этого подтверждать
удаление временных файлов AI Core нельзя.

Если ACK не дошёл или потерялся ответ, ожидающее подтверждение остаётся в БД.
Фоновое восстановление выбирает его и после перезапуска процесса, отправляя
не более четырёх ACK одновременно. Повторный ACK допустим по контракту AI Core.
При `204` ожидание снимается. При `409 RESULTS_EXPIRED` сохраняется диагностическая
причина, ожидание снимается; уже сохранённые пять фото и `COMPLETED` остаются.
Остальные ошибки сохраняют ожидание до следующей попытки.

Для временных ошибок первой отправки, опроса, скачивания и ACK сохраняется время
повторной попытки. Учитывается целочисленный `Retry-After` от AI Core, иначе
используется интервал восстановления (по умолчанию 30 секунд). Ожидание хранится
в БД, а не занимает спящий HTTP-запрос. Для активной генерации общий срок
выполнения имеет приоритет над длительной паузой. Для ACK готового альбома этот
срок не применяется. Несколько процессов могут повторить ACK одновременно;
это безопасно благодаря его идемпотентности.

Миграция не назначает ACK старым завершённым альбомам: нельзя достоверно понять,
был ли он уже отправлен. Новый механизм действует на завершения после обновления.

## Ограничение на стороне AI Core

Когда remote `job_id` сохранён, восстановление использует GET существующего
задания, не создавая новую генерацию. Если ответ первого POST потерялся до
сохранения ID, backend повторяет неизменный запрос с тем же Idempotency-Key.
Однако текущий AI Core имеет ограничение повторного POST для `COMPLETED/AVAILABLE`:
он может вернуть `503` вместо исходного задания. Backend не может надёжно
восстановить неизвестный ID, пока AI Core не исправит повтор POST или не добавит
поиск по ключу. Создание нового ключа автоматически недопустимо: оно запустит
дубликат. Это ограничение не устранено настройкой LAN или повтором ACK.
