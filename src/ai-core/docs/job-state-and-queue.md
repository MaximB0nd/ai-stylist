# Хранение состояния и очередь AI Core

## 1. Где хранится состояние

AI Core использует собственную постоянную базу PostgreSQL. Очередь является частью
AI Core и строится поверх записей в этой базе. Состояние не хранится только в
памяти процесса или только в Redis: после перезапуска ни задание, ни уже принятые
результаты не должны потеряться.

Для первой версии отдельный брокер сообщений не нужен. Он может появиться позже,
если измерения покажут, что очередь в PostgreSQL не обеспечивает требуемую
пропускную способность.

## 2. Минимальные таблицы

### 2.1. `ai_jobs`

Одна строка на задание:

- внутренний `job_id`;
- хеш ключа защиты от повторов;
- текущее состояние;
- запрошенное и принятое количество изображений;
- версия входного договора;
- безопасная копия параметров задания без временных ссылок;
- внутренние ключи временных копий исходных фотографий;
- время создания, изменения и завершения;
- текущий исполнитель, номер аренды и срок аренды;
- код последней ошибки;
- признак отмены;
- срок очистки временных данных.

### 2.2. `ai_job_images`

Одна строка на каждое место результата от `0` до
`requested_image_count - 1`:

- номер места;
- состояние подготовки результата;
- зарезервированный `OutfitSpec` и его версия;
- число попыток;
- модель, версия инструкции и `seed`;
- ключ временного объекта и контрольная сумма;
- безопасный код последней ошибки.

### 2.3. `ai_job_attempts`

История ограниченных попыток:

- этап обработки;
- номер попытки;
- начало и окончание;
- результат;
- код ошибки;
- использованная версия модели.

История нужна для разбора ошибок и расчёта стоимости. Она не содержит изображения,
временные ссылки и полный пользовательский текст.

### 2.4. `ai_outfits`

Зарезервированные комплекты текущего задания:

- `job_id`;
- `outfit_id`;
- нормализованные признаки комплекта;
- хеш признаков для поиска точных повторов;
- состояние резервирования.

Резервирование выполняется одной операцией в базе до запуска генерации. Поэтому
параллельные исполнители не получают один и тот же комплект.

### 2.5. `ai_status_events`

Неотправленные и подтверждённые уведомления основному серверу:

- уникальный `event_id`;
- `job_id`;
- возрастающий номер `sequence`;
- состояние и краткий ход выполнения;
- число попыток доставки;
- время следующей отправки;
- время подтверждения.

Изменение задания и создание события выполняются в одной операции базы. Поэтому
сбой процесса между ними не приводит к потере уведомления.

## 3. Как исполнитель получает задание

1. Исполнитель выбирает доступное задание с блокировкой строки.
2. В той же операции записывает себя владельцем аренды.
3. Увеличивает номер аренды и задаёт срок её действия.
4. Во время работы продлевает аренду.
5. Каждое сохранение результата содержит номер текущей аренды.

Если исполнитель перестал продлевать аренду, другой исполнитель получает задание
с новым номером. Результат со старым номером отклоняется. Это не позволяет старому
процессу перезаписать более новое состояние.

В PostgreSQL получение задания может быть реализовано через блокировку строк с
пропуском уже занятых записей. Точный запрос относится к этапу реализации.

## 4. Восстановление после сбоя

После запуска AI Core:

1. находит задания с истёкшей арендой;
2. проверяет сохранённое состояние каждого места результата;
3. не повторяет уже принятые изображения;
4. возвращает незавершённые места в очередь;
5. продолжает доставку неподтверждённых уведомлений;
6. ставит бесхозные временные объекты на удаление.

Задание становится `COMPLETED` одной операцией только после того, как все места
результата приняты и сохранены. Повтор той же операции возвращает уже записанный
результат и не создаёт дубликаты.

## 5. Временные файлы

AI Core хранит временные данные по пути, содержащему только его внутренние
идентификаторы:

```text
temporary/{job_id}/{lease_number}/{result_index}/...
```

AI Core отвечает за:

- временные копии исходников;
- промежуточные изображения;
- результаты неудачных попыток;
- объекты, записанные исполнителем до сбоя;
- очистку после `COMPLETED`, `FAILED` и `CANCELLED`.

Основной сервер отвечает за постоянные исходники, альбомы и принятые итоговые
изображения. AI Core не удаляет их при очистке своего задания.

## 6. Защита данных

- Временные ссылки не записываются в журналы и историю попыток.
- Изображения и пользовательские описания не попадают в технические события.
- Временное хранилище закрыто от общего доступа.
- Каждый исполнитель получает доступ только к объектам своего задания.
- Срок очистки задаётся настройками AI Core.
- Неудачное удаление повторяется и отражается в наблюдении за системой.
