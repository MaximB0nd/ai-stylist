# Хранение состояния и очереди AI Core

## 1. Разделение состояния

AI Core не имеет одной общей базы для всех служб.

- Главный оркестратор хранит полное состояние задания и порядок этапов в своей
  PostgreSQL.
- Каждый групповой оркестратор хранит в своей PostgreSQL только локальные запуски
  этапа, попытки воркеров, входящие и исходящие сообщения.
- Воркеры не имеют собственной предметной базы и не имеют доступа к базам
  оркестраторов.
- RabbitMQ переносит сообщения между уровнями, но не является источником
  состояния.

Служба API читает и меняет состояние только через внутренний интерфейс главного
оркестратора.

## 2. База главного оркестратора

### 2.1. `ai_jobs`

Содержит `job_id`, хеш ключа защиты от повторов, текущее состояние, запрошенное и
принятое количество результатов, версию договора, время, ошибку, отмену и срок
очистки.

### 2.2. `ai_job_images`

Содержит место результата, состояние, зарезервированный `OutfitSpec`, число
запусков этапов, версии модели и инструкции, `seed`, ключ принятого объекта,
контрольную сумму и последнюю безопасную ошибку.

### 2.3. `ai_stage_runs`

Одна строка на запуск функциональной группы:

- `stage_run_id`, `job_id`, тип этапа и место результата;
- состояние и номер запуска;
- текущий `lease_token` и срок выполнения;
- идентификатор группового оркестратора;
- итог этапа и безопасный код ошибки.

Главный оркестратор не хранит детали отдельных попыток воркеров.

### 2.4. `ai_outfits`

Содержит зарезервированные комплекты задания. Уникальное ограничение на
нормализованный хеш не позволяет принять повтор. Резервирование выполняется
главным оркестратором между этапами стилиста и генерации.

### 2.5. `ai_status_events`

Содержит неизменяемые события для основного сервера: `event_id`, `job_id`,
возрастающий `sequence`, состояние и время. Доставкой управляет группа
уведомлений.

## 3. База каждого группового оркестратора

У каждой группы отдельная база или отдельная изолированная база данных с одним
владельцем. Минимальные таблицы одинаковы:

### 3.1. `stage_requests`

Полученный от главного оркестратора `stage_run_id`, состояние обработки, входные
параметры, срок и итог группы. Повторная команда с тем же `stage_run_id` возвращает
сохранённый итог и не создаёт второй запуск.

### 3.2. `worker_attempts`

Попытки воркеров: номер, `lease_token`, срок, версия воркера и модели, состояние,
время и безопасная ошибка.

### 3.3. `inbox`

Уже обработанные `message_id`. Идентификатор сообщения и изменение локального
состояния записываются одной операцией.

### 3.4. `outbox`

Команды воркерам и итоги главному оркестратору. Изменение локального состояния и
запись исходящего сообщения выполняются одной операцией. Отдельный отправитель
публикует записи в RabbitMQ с подтверждением.

## 4. Очереди RabbitMQ

Для каждой группы есть две пары очередей:

1. между главным и групповым оркестраторами — `ai.stage.*`;
2. между групповым оркестратором и его воркерами — `ai.worker.*`.

Точные имена находятся в [договоре сообщений](message-contracts.md).

Очереди и сообщения сохраняются на диске. Получатель подтверждает сообщение после
сохранения входа и исходящего ответа. Неподтверждённая команда после остановки
процесса выдаётся другой копии той же службы. После исчерпания технических
повторов сообщение попадает в очередь ошибок своей группы.

## 5. Аренда и устаревшие результаты

Главный оркестратор создаёт `stage_run_id` и аренду запуска группы. Групповой
оркестратор создаёт отдельный `lease_token` для каждой попытки воркера.

Результат воркера принимается группой только с текущим токеном попытки. Итог
группы принимается главным оркестратором только с текущими `stage_run_id` и
токеном запуска этапа. Таким образом, старый воркер или старый групповой
оркестратор не может перезаписать новое состояние.

## 6. Восстановление после сбоя

После запуска каждый оркестратор:

1. публикует неотправленные записи своей таблицы `outbox`;
2. находит истёкшие аренды, которыми владеет;
3. создаёт новую попытку только для незавершённой работы;
4. сохраняет поздние ответы как устаревшие без изменения результата;
5. продолжает обработку сообщений из своей очереди ошибок только после решения
   оператора или отдельной безопасной процедуры.

Главный оркестратор не повторяет уже принятые изображения. Задание становится
`COMPLETED` одной операцией только после принятия ровно запрошенного количества
результатов.

## 7. Отмена

Главный оркестратор записывает `CANCELLED` и больше не создаёт этапы. Для активных
`stage_run_id` он отправляет отмену соответствующим групповым оркестраторам.
Группа запрещает новые попытки воркеров и игнорирует поздние результаты. Даже если
отмена не дошла сразу, главный оркестратор не принимает итог отменённого запуска.

После отмены отдельно запускаются группа уведомлений и группа очистки. Очистка
касается только временной области AI Core.

## 8. Временные файлы и защита данных

```text
temporary/{job_id}/{stage_run_id}/{result_index}/{attempt}/...
```

- Воркеры получают ограниченные ссылки только на объекты своей команды.
- Групповые оркестраторы хранят ключи объектов, но не постоянные учётные данные
  общего хранилища.
- Временные ссылки, фотографии и полный пользовательский текст не попадают в
  журналы.
- Воркеры очистки удаляют только область `temporary/` AI Core.
- Постоянные исходники, альбомы и готовые изображения удаляет основной сервер.
