# Последовательность разработки AI Core

## 1. Документы и договоры

- зафиксировать общую архитектуру отдельно от внешнего договора;
- завести отдельную папку документации для каждого микросервиса;
- зафиксировать форматы создания, чтения, отмены и уведомлений;
- зафиксировать сообщения между главным оркестратором, групповыми оркестраторами
  и воркерами;
- описать состояния, восстановление, повторы и отмену;
- описать `OutfitSpec` версии 1 и таксономию одежды;
- описать настройки каждой службы и допустимое количество изображений;
- подготовить план проверки моделей и распределённого конвейера.

Документы AI Core являются исходным договором для интеграции. Основной сервер
подстраивает свою реализацию под опубликованную версию внешнего договора.

## 2. Проверка моделей

- собрать закрытый набор с согласием участников;
- подготовить обезличенное описание набора;
- реализовать воспроизводимый запуск проверки;
- сравнить модели стилиста, генерации и проверки по единым правилам;
- выбрать модели и минимальное оборудование по заранее записанным показателям;
- проверить, что каждая модель запускается внутри отдельного воркера.

## 3. Последовательный опытный образец

- реализовать формирование и проверку `OutfitSpec`;
- последовательно создать одно изображение за раз;
- сохранять версии модели, инструкции, `OutfitSpec` и `seed`;
- подключить базовую проверку качества и безопасности;
- подтвердить достижимость требуемого количества результатов.

Опытный образец может запускаться локально, но код этапов сразу отделяется так,
чтобы его можно было перенести в соответствующий микросервис.

## 4. Основа распределённой системы

- развернуть PostgreSQL главного оркестратора и изолированные базы групп;
- развернуть RabbitMQ с постоянными очередями и очередями ошибок;
- реализовать общую библиотеку договоров сообщений без логики отдельных служб;
- реализовать таблицы входящих и исходящих сообщений;
- добавить версии сообщений, защиту от повторов и `lease_token`;
- настроить единые журналы, показатели и идентификатор связи сообщений.

## 5. Управляющие микросервисы

- реализовать службу API по внешнему договору;
- реализовать главный оркестратор и внутренний интерфейс для службы API;
- реализовать создание, чтение, отмену и точное завершение задания;
- реализовать резервирование неповторяющихся комплектов;
- реализовать восстановление после сбоя и повторную публикацию команд;
- развернуть несколько копий и проверить согласованность через PostgreSQL.

## 6. Функциональные группы

Для каждого этапа сначала создаётся отдельный групповой оркестратор, затем
отдельный воркер:

1. оркестратор и воркер подготовки фотографий;
2. оркестратор и воркер стилиста;
3. оркестратор и воркер генерации изображения;
4. оркестратор и воркер проверки результата;
5. оркестратор и воркер очистки временных данных;
6. оркестратор и воркер доставки уведомлений.

Для каждой группы требуются собственная база, две пары очередей, настройки,
проверка готовности, показатели и проверка повторной доставки на обоих уровнях.

## 7. Проверка на разных хостах

- запустить RabbitMQ, главную базу, API и главный оркестратор отдельно;
- разместить каждый групповой оркестратор отдельно от его воркеров;
- разместить стилист, генератор и проверку на разных хостах;
- добавить и убрать копию каждого воркера без остановки конвейера;
- проверить остановку воркера во время команды;
- проверить перезапуск RabbitMQ, главного и каждого группового оркестратора;
- убедиться, что повторные сообщения не создают двойных результатов;
- измерить очередь, задержку, использование ресурсов и стоимость этапов.

## 8. Повышение качества и мощности

- улучшать сохранение лица и телосложения по результатам полной проверки;
- увеличивать число копий только перегруженного типа воркера;
- при нехватке памяти распределять одну модель внутри копии воркера по группе GPU;
- повторять полный прогон перед сменой модели или договора сообщения;
- учитывать пользовательские оценки отдельно от закрытого набора.

## 9. Расширение сценариев

- поддержать фотографии конкретных предметов одежды;
- при необходимости добавить отдельный микросервис виртуальной примерки;
- интегрировать каталог реально доступной одежды;
- добавлять новый этап только через новую очередь и версионируемый договор, не
  создавая прямые вызовы между воркерами.
