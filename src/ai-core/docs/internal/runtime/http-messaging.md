# HTTP-обмен оркестратора и воркеров в MVP

## Граница

Оркестратор сохраняет решение о команде и состояние задания в одной транзакции
PostgreSQL. Отдельный доставщик выбирает команды из одной таблицы по `stage` и
отправляет их по HTTP. RabbitMQ в этом MVP нет. Воркеры не обращаются друг к
другу и не получают доступ к PostgreSQL оркестратора.

В этом MVP сервисы не проверяют токены авторизации. Доступ к ручкам ограничен
внутренней сетью. При подключении авторизации потребуется отдельное изменение
договора.

## Команда

Каждый воркер принимает `POST /internal/v1/commands` с JSON-телом:

| Поле | Правило |
| --- | --- |
| `contract_version` | `1` |
| `command_id` | UUID одной логической попытки выполнения |
| `job_id` | UUID задания |
| `stage` | `PREPARATION`, `STYLING`, `GENERATION`, `VERIFICATION` или `NOTIFICATION` |
| `attempt` | номер логической попытки, начиная с `1` |
| `order_index` | `null` для подготовки и уведомления; индекс изображения `0..N-1` для остальных |
| `payload` | данные этапа по таблице ниже |

Ответ `202` означает приём команды, а не успешное выполнение. Повтор с тем же
`command_id` должен быть безопасен: воркер не создаёт новый логический
результат и повторно передаёт ранее полученный результат, если он уже готов.
Неизвестная версия или неверное тело дают `400`, временная неготовность —
`503`. Ошибки имеют поля `code`, `message`,
`retryable`; сообщения не содержат ссылок и пользовательского текста.

## Результат

Воркер вызывает `POST /internal/v1/worker-results` оркестратора:

| Поле | Правило |
| --- | --- |
| `contract_version` | `1` |
| `message_id` | UUID доставки результата |
| `command_id`, `job_id`, `stage`, `attempt`, `order_index` | совпадают с командой |
| `status` | `SUCCEEDED` или `FAILED` |
| `result` | объект результата при успехе, иначе `null` |
| `error` | `code`, `message`, `retryable` при ошибке, иначе `null` |

Первое применение текущего результата атомарно записывает состояние,
идентификатор обработанного сообщения и следующие команды. Ответ — `204`.
Повтор сообщения или поздний результат завершённой/заменённой попытки также
получает `204`, но состояние не меняет. Неизвестная команда даёт `404`,
несовпадение полей команды — `409`. Воркер повторяет callback при сетевой
неопределённости до `204`.

## Доставка и попытки

- Если после `202` результата нет 30 минут, доставщик повторяет тот же
  `command_id`. Это повтор доставки, не новая попытка выполнения.
- Перед повторной отправкой оркестратор может обновить истёкшие короткие
  ссылки через службу временных файлов. Идентификаторы файлов, `command_id`
  и остальные параметры работы остаются теми же; воркер принимает новые
  ссылки для ещё не завершённой команды.
- Только результат `FAILED` с `retryable: true` создаёт новую логическую
  попытку с новым `command_id`. Максимум четыре попытки на этап для одного
  места; интервалы перед попытками 2–4: 5, 30 и 120 секунд.
- Результат с `retryable: false` или исчерпание попыток завершает задание
  `FAILED`, кроме уведомления: его событие помечается недоставленным.
- Пока результат отсутствует, доставка того же `command_id` продолжается до
  результата либо конечного состояния задания. Общий срок задания — 24 часа.
- Для `NOTIFICATION` неудачный HTTP-вызов расходует попытку доставки события;
  после четырёх неудач событие становится `UNDELIVERED`. Принятое воркером
  событие ждёт callback; отсутствие результата ограничено 24 часами от создания
  события. Статус задания при этом не меняется.
- После перезапуска оркестратор восстанавливает неотправленные команды,
  ожидание результата и сроки из PostgreSQL.

## Данные этапов

| Этап | `payload` команды | `result` успеха |
| --- | --- | --- |
| `PREPARATION` | `face` и `body`: `artifact_id`, короткая `read_url`; `prepared_face` и `prepared_body`: `artifact_id`, короткая `write_url` | `prepared_face`, `prepared_body`: `artifact_id`, `checksum_sha256`, `size_bytes`, `format`, `width`, `height` |
| `STYLING` | приведённые `person`, `preferences`, массив хешей уже занятых комплектов `reserved_outfit_hashes` | `outfit_spec_version`, непустой структурированный объект `outfit_spec`, `model_version`, `prompt_version` |
| `GENERATION` | короткие ссылки на подготовленные фото, `outfit_spec_version`, `outfit_spec`, `seed`, `candidate_artifact_id`, короткая `write_url` | `artifact_id`, `checksum_sha256`, `size_bytes`, `format`, `width`, `height`, `model_version`, `prompt_version`, `seed` |
| `VERIFICATION` | короткие ссылки на исходные фото и кандидата, `outfit_spec_version`, `outfit_spec` | `verdict`: `ACCEPTED`, `REJECTED` или `INCONCLUSIVE`; `reason_codes` и `policy_version` |
| `NOTIFICATION` | неизменяемое событие внешнего договора (`event_id`, `job_id`, `sequence`, `status`, `progress`, `occurred_at`, `error`) | `event_id`, `http_status`, `delivered_at` при успешном `2xx` |

Уведомления одного задания передаются по `sequence`: следующее событие ждёт,
пока предыдущее станет `DELIVERED` или `UNDELIVERED`.

`outfit_spec` передаётся без изменения между стилистом, генерацией и
проверкой. Оркестратор вычисляет SHA-256 его приведённого JSON вместе с
`outfit_spec_version` и резервирует этот хеш для задания. Схему элементов
комплекта и правила модельной оценки определят договоры соответствующих
воркеров; оркестратор требует непустой объект и не интерпретирует одежду.
Если хеш уже зарезервирован, результат стилиста не принимается и создаётся
следующая попытка `STYLING` в пределах общего лимита этапа.

После `REJECTED` создаётся новый кандидат с новым `artifact_id` и тем же
комплектом; не более трёх кандидатов на изображение. После `INCONCLUSIVE`
создаётся новая попытка `VERIFICATION` с новым `command_id` для того же
кандидата в пределах четырёх попыток проверки.
Ошибка генерации повторяет тот же комплект и сохраняет `artifact_id` для той
же попытки записи. Принятые изображения обрабатываются последовательно.
