# Вызовы processing services

## Назначение

- Главный оркестратор вызывает processing services по внутреннему HTTP.
- Службы отвечают синхронно по собственным договорам.
- Службы не вызывают друг друга и не знают полный процесс.
- Файлы передаются по коротким ссылкам, а не через оркестратор.

Общие правила запросов, ответов и ошибок определяет
[договор processing services](../services/CONTRACT.md).

## Ответственность оркестратора

- выбрать следующую службу;
- создать уникальный `request_id`;
- получить короткие ссылки на чтение и запись;
- выбрать доступный экземпляр по service discovery и свежему status либо
  вызвать логический endpoint за внутренним балансировщиком;
- задать таймаут вызова;
- сохранить результат до запуска следующего этапа;
- повторить только временную ошибку;
- не применять результат отменённого или устаревшего вызова;
- ограничить число одновременных вызовов каждой службы.

## Capacity и выбор экземпляра

- `GET /health/status` описывает только один экземпляр и только момент ответа.
- `IDLE` и `BUSY` с `accepting_requests: true` являются кандидатами для вызова;
  `STARTING`, `SATURATED`, `DRAINING` и `UNAVAILABLE` новые вызовы не принимают.
- Status не резервирует capacity. После выбора рабочий endpoint может вернуть
  `429 CAPACITY_EXCEEDED`, если последний слот занял другой вызов.
- При `429` оркестратор использует `Retry-After`, пробует другой экземпляр или
  оставляет этап ожидающим; модельная попытка ещё не началась.
- Отсутствие HTTP-ответа означает наблюдаемое `UNREACHABLE`. Такой экземпляр
  временно исключается из выбора средствами service discovery или
  балансировщика.
- При работе через балансировщик оркестратор не перечисляет реплики и не хранит
  их статусы в PostgreSQL.

## Повтор

- Повтор одного HTTP-вызова может произойти после таймаута или временной ошибки.
- Оркестратор сохраняет тот же логический выход и передаёт новый `request_id`,
  если это новая попытка.
- Служба не хранит состояние попыток и не решает, нужен ли следующий повтор.
- Для недетерминированной модели оркестратор сохраняет `seed` попытки.

## Возможный транспортный адаптер

Очередь не входит в договор processing service. Если распределённому размещению
потребуется RabbitMQ или другой брокер, отдельный адаптер:

1. получает транспортное сообщение;
2. вызывает HTTP API службы;
3. публикует HTTP-результат в транспорт;
4. выполняет подтверждение сообщения.

Служба и её HTTP-договор при этом не меняются. Формат очереди, подтверждения и
повторная доставка относятся к договору адаптера и принимающей системы.
