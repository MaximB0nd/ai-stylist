# Договор главного оркестратора

## HTTP

| Правило | Значение |
| --- | --- |
| Сеть | внутренняя |
| Формат | `application/json` |
| Авторизация | `Bearer <internal-token>` |

| Метод | Вход | Результат |
| --- | --- | --- |
| `POST /internal/v1/jobs` | `idempotency_key_hash`, `request_hash`, приведённый запрос | `201`; повтор — `200` |
| `GET /internal/v1/jobs/{job_id}` | `job_id` | публичное представление |
| `POST /internal/v1/jobs/{job_id}/cancel` | пустой объект | публичное представление |
| `POST /internal/v1/jobs/{job_id}/results/ack` | пустой объект | `204` |

## Повтор создания

| Условие | Результат |
| --- | --- |
| новый `idempotency_key_hash` | создать задание |
| тот же ключ и `request_hash` | вернуть задание |
| тот же ключ, другой `request_hash` | `409` |

Оба хеша — SHA-256 в шестнадцатеричном виде. Исходный ключ не хранится.

## Ошибки

| HTTP | Условие |
| ---: | --- |
| `400` | неверный внутренний запрос |
| `401` | неверный токен |
| `404` | нет задания |
| `409` | конфликт ключа или состояния |
| `503` | неготовность |

Формат: `code`, `message`, `retryable`.

## Импорт входов

- После сохранения задания оркестратор создаёт отдельные стабильные
  `artifact_id` для фотографий лица и полного роста.
- Для каждого входа он вызывает
  `POST /internal/v1/artifacts/{artifact_id}/import`, передавая исходный URL из
  задания и допустимый предел байтов. Импорты можно выполнять параллельно.
- HTTP `201` и `200` являются успешным импортом. Оркестратор сохраняет checksum,
  фактический media type, размер и геометрию опубликованного файла.
- Повтор использует тот же `artifact_id`. Только временные ошибки с
  `retryable: true` повторяются с учётом `Retry-After`.
- Окончательная ошибка импорта завершает задание как `FAILED`; оркестратор
  удаляет уже импортированный парный вход и не запускает processing services.
- Ни один processing service не запускается, пока требуемые ему входы не
  опубликованы. Службам передаются только ссылки artifact service, но не
  исходные URL основного сервера.

## Processing services

- Общие правила: [договор processing services](../CONTRACT.md).
- Порядок вызовов: [messaging.md](../../runtime/messaging.md).
- Полезная нагрузка: договор соответствующей службы.
- До HTTP-вызова с записью создать `artifact_id` и запросить короткую ссылку.
- Каждая принятая попытка с файловым результатом использует новый `request_id`,
  новый output `artifact_id` и новую ссылку записи. `429 CAPACITY_EXCEEDED`,
  полученный до admission, не создаёт попытку модели и может использовать уже
  подготовленное место записи.
- Оркестратор применяет только результат текущей попытки. Поздний ответ после
  timeout не меняет состояние задания, а связанный с ним output `artifact_id`
  ставится на удаление.
- При прямой адресации экземпляров оркестратор рассматривает только status с
  `accepting_requests: true` и положительной `available_capacity`. Status имеет
  короткий срок жизни и не сохраняется как durable state задания.
- При размещении экземпляров за внутренним балансировщиком выбор экземпляра
  принадлежит балансировщику; оркестратор вызывает логический endpoint службы.
- Рабочий вызов является единственным атомарным admission. Ответ
  `429 CAPACITY_EXCEEDED` означает, что слот не был получен. Оркестратор выбирает
  другой доступный экземпляр либо ждёт `Retry-After`; попытка inference при этом
  не считается начатой.
- Timeout, connection refused и отсутствие ответа status означают наблюдаемое
  `UNREACHABLE`. Оркестратор не ожидает, что упавший процесс сообщит `FAILED`.
- Конечные состояния: [внешний договор](../../../public/ai-core-api/CONTRACT.md#получение-состояния).
