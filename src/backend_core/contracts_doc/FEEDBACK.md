# Обратная связь

## Назначение

Авторизованный пользователь отправляет имя, контактную почту и комментарий.
Обращение сохраняется в PostgreSQL и связывается с пользователем из JWT.
Контактные данные могут отличаться от профиля; профиль не изменяется.
Один пользователь может отправить несколько обращений.

## HTTP API

`POST /api/v1/feedback`

Заголовки:

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

Тело запроса:

```json
{
  "name": "Иван Петров",
  "email": "ivan@example.com",
  "comment": "Комментарий о работе сервиса"
}
```

| Поле | Проверка |
|---|---|
| `name` | Обязательная строка, 1–100 символов после `strip()` |
| `email` | Обязательный `EmailStr`, до 254 символов после валидации |
| `comment` | Обязательная строка, 1–5000 символов после `strip()` |

Пробелы по краям имени и комментария удаляются. Пустой текст и неизвестные поля
отклоняются. `user_id` нельзя передавать в теле: связь устанавливает сервер.
Проверка email подтверждает формат, но не существование ящика и не владение им.
Email нормализуется библиотекой `email-validator`; локальная часть не приводится
принудительно к нижнему регистру.

### Успех — 201 Created

```json
{
  "id": "12345678-1234-4234-8234-123456789abc",
  "created_at": "2026-10-19T10:00:00Z"
}
```

Ответ выдаётся после commit. Он не содержит контактные данные, комментарий
или идентификатор пользователя. Время содержит часовой пояс; конкретная форма
его записи может быть `Z` или `+00:00`.

### Ошибки

- `401` — отсутствующий, неверный или просроченный JWT, отсутствующий или неактивный пользователь.
- `422` — неверные поля, превышение длины, пустой текст, дополнительные поля.
- `503` — ошибка SQLAlchemy при сохранении: `Could not save feedback. Please try again later.`
  Внутренние сообщения БД в ответ не включаются.

Повторная отправка создаёт новое обращение. Отдельная идемпотентность пока не реализована;
при потере ответа после commit повтор может создать вторую запись.

## PostgreSQL

Таблица `feedback`:

| Поле | Тип и назначение |
|---|---|
| `id` | UUID, первичный ключ |
| `user_id` | UUID NOT NULL, FK `users.id`, индекс `ix_feedback_user_id` |
| `name` | VARCHAR(100) NOT NULL |
| `email` | VARCHAR(254) NOT NULL |
| `comment` | TEXT NOT NULL |
| `created_at` | TIMESTAMP WITH TIME ZONE NOT NULL, серверное значение времени |

Физическое удаление пользователя удаляет его отзывы через `ON DELETE CASCADE`.
Деактивация пользователя отзывы не удаляет. Ограничения PostgreSQL дополнительно
проверяют длины полей; проверка формата email выполняется на уровне API.

Сохранение: `add → flush → refresh → commit`. Серверные поля загружаются до commit.
При исключении выполняется rollback. Сессия приложения использует
`expire_on_commit=False`, поэтому ответ не требует дополнительного чтения после commit.

## Устройство

- `app/api/v1/endpoints/feedback.py` — маршрут и аутентификация.
- `app/schemas/feedback.py` — валидация и ответ.
- `app/services/feedback_service.py` — сценарий создания и безопасная ошибка БД.
- `app/db/repositories/feedback_repository.py` — транзакция сохранения.
- `app/models/feedback.py` — модель PostgreSQL.
- `app/core/dependencies.py` — сборка зависимостей.
- `alembic/versions/0006_feedback.py` — миграция `0005 → 0006`.

Комментарий хранится как обычный текст, без выполнения и интерпретации HTML.
Будущая админ-панель должна выводить его с экранированием, без вставки через `innerHTML`.
Операции просмотра, изменения и удаления отзывов через API, отправка писем и
административная панель в этот этап не входят.

## Миграция и запуск

Из `src/backend_core` с настроенным окружением и существующей базой:

```bash
python -m alembic upgrade head
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Для Docker из корня проекта:

```bash
docker compose up -d --build backend_core
```

Compose-команда backend сама выполняет проверку baseline и миграции перед Uvicorn.
Сборка образа сама по себе схему БД не обновляет. Существующие записи пользователей
и альбомов при upgrade сохраняются. Downgrade до `0005` удаляет таблицу отзывов
вместе с её содержимым; его нельзя использовать для обычного перезапуска.

## Проверки

```bash
python -m pytest tests/test_feedback.py -v
python -m pytest tests -q
```

Изолированные проверки покрывают валидацию, границы, JWT, привязку к пользователю,
повторные обращения, сохранение обычного текста и ошибки транзакции.
Интеграционная проверка PostgreSQL описана в `tests/test_feedback_postgres.py`:
она использует отдельную временную базу, не рабочую базу проекта.

Для неё задайте `FEEDBACK_TEST_DATABASE_URL` — URL тестового PostgreSQL,
пользователь которого имеет право `CREATE DATABASE`, затем выполните:

```bash
python -m pytest tests/test_feedback_postgres.py -v
```

Проверка сама создаёт базу `feedback_test_<uuid>`, применяет миграции, проверяет
HTTP-сохранение и чтение в новой сессии, внешний ключ, каскадное удаление,
downgrade/upgrade и удаляет только эту временную базу. Без переменной она пропускается.
В Backend Tests на GitHub Actions тестовая PostgreSQL и эта переменная подключены
автоматически, поэтому новая интеграционная проверка выполняется вместе с остальными тестами.
